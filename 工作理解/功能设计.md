# Saas用户体系设计

## 流派一： 孤岛模型（The Silo Model）-早期Slack/传统ERP

在早期的 Slack 或很多私有化部署转 SaaS 的系统中，即便你是同一个自然人，想加入 A公司和 B公司，你必须注册两个账号哪怕用同一个邮箱，密码也可以不同)。

* 设计逻辑:。
  。用户表的唯一索引是(tenant_id, email)。
  。A租户的 sys_user 表里有你，B 租户的 sys_user 表里也有你。
  。他们在物理上是两行完全不同的数据，ID不同，没有任何关联。。
* 优点:
  。数据隔离最彻底:绝对不会出现“我在 A 公司改了头像，B 公司也变了”的问题。。架构简单:不需要考虑复杂的全局 Session 切换。。
* 缺点:
  。用户体验极差:切换租户需要退出重新登录，或者同时维护多套密码。
  。无法做平台级画像:平台方无法统计“这个用户到底活跃在多少个企业里"。
* 适用场景:。
  。强安全、强保密的金融级 SaaS。
  。不需要跨租户协作的系统。

## 二、升级后的 ER 数据模型
我们需要把之前的“扁平化租户"拆解。
**1.全局层(Global)**

* uc_user(自然人表)
  全平台共享，手机号唯一。存储mobile,password，wx_openid。

**2.SaaS 租户层(SaaS Tenant Layer)**

* sys_tenant(SaaS租户表-物业方).
  id:SaaS租户ID(如:T001万科物业)
  license_limit:许可包含的园区数量、账号数量上限。
  admin_user_id:超级管理员。

**3.物理园区层(Project Layer)**

* sys_project(项目/园区表)
  id:项目ID(如:P101深圳湾一号)
  tenant id:所属SaaS租户(T001)
  project_name:园区名称。
  。业务意义: 很多大型物业集团(SaaS租户)名下管理着几十个园区(Project)，数据既要独立又要能由集团汇总。

**4.业务资源层(Business Layer)**

* biz_company(入驻企业表-原“租户")。
  id:企业ID(如:C999 腾讯)
  project id:所属园区(P101)
  tenant id:冗余字段，方便查询(T001)
  company_name:企业名称。
  room no:房号(关联楼宇资源)。
